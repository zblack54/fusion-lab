## Architecture options

| Option | Benefit | Cost and disposition |
|---|---|---|
| Worker edits; trusted host captures and commits an immutable candidate | Keeps Git/control writes out of inference and fits the current authorized host chat | Recommended; requires a controlled lifecycle/bridge revision and native commit/crash evidence |
| Host copies approved candidate into a separate clean trusted staging checkout/repository before committing | Stronger separation from mutable worker files and clearer recovery | Viable variant; more storage/transfer and exact-tree mapping. Preserve original checkout evidence and never apply an unreviewed patch. |
| Continue unchanged-head output then CreatePr | Smallest code change | Reject: observed sentinel is untracked and absent from that commit. A PR/head attestation would conceal uncommitted work. |
| Enable Git writes through overrides/add-dir, full access, or out-of-sandbox tool approval | Might allow worker commit | Outside authorization and not proposed. No experiments with this route. |

Recommend immutable capture plus a trusted host-owned commit adapter using the existing host chat, not another inference process and not invented native GitHub credentials. The host already has authorized local tools and the GitHub connector; its exact implementation must be explicit in the formal revision. It never interprets worker output as an executable shell command or remote authority.

## Proposed edit, capture and approval lifecycle

All behavior below is proposed, not present in the approved revision2 implementation.

1. Before workspace launch, hold the canonical checkout lease and record base HEAD, branch/ref identity, scope digest, task, attempt generation and owner. Require a clean index and tracked working tree and no nonignored untracked files. Reject dirty input rather than stage another person's work. Inventory ignored paths separately so they cannot silently enter a commit. Do not reset, stash, clean or delete an existing tree. A dedicated checkout is the intended domain.
2. Worker runs under the unchanged workspace-write boundary. Its terminal result means edits_ready, with observed base HEAD/checkpoint; it is not a commit or publication claim. Unexpected HEAD movement fails closed. Cancellation/nonzero/malformed output retains failure and files; it never auto-commits partial work. Existing read-only changed-HEAD rejection remains in force.
3. Confirm root reaped and zero descendant membership before examining candidate files. Under the same logical checkout fence, capture changed tracked files, deletions and all nonignored untracked files, with a complete before/after status inventory. A tracked rename is represented by exact old deletion/new content; do not trust rename heuristics for authority. Include staged/index anomalies as rejection because the worker should not have altered protected metadata.
4. Construct a private immutable manifest with task/issue/scope, checkout identity, attempt/owner/generation, base parent/tree, ordered normalized relative paths, old/new file modes and blob identities, raw byte lengths/SHA256, deletions, and captured content references. Capture old status/base inventory too. Use bounded streaming reads, checked cumulative limits, regular-file handles and cap+1 growth checks. Hash copied content outside the checkout; validate identity/type through opened handles, not a pre-open path check alone. A changed file/list during capture rejects or requires owner inspection; no live-file staging after approval. Record the manifest hash and durable awaiting_commit state atomically before exporting anything.
5. Export one fixed typed CommitCandidate intent keyed by task + generation + base + manifest digest. Its payload references private captured blobs, scope and diff; no worker-provided command text or arbitrary output path. The host loads and validates the same bound scope, independently reviews the complete diff and path inventory against instructions/non-goals/locked-file ownership, and records approval bound to that exact manifest. Prose approval is not mechanically proved by SHA256. A machine path allowlist can reinforce scope only when explicitly host-approved; do not invent it from an LLM answer.
6. Host builds the exact approved tree, commits it with the base as sole parent, then returns typed Commit evidence. Only after validating that evidence and independently observing the resulting Git object/ref may the supervisor set ImplementedUnverified and export CreatePr for the NEW head. An unchanged HEAD with dirty edits, missing manifest, no-op tree or missing commit evidence cannot produce a publishable intent. A successful read-only/no-change report is not an implementation commit; its eventual report-only disposition must be made explicit in the revision, not silently accepted as a PR.

Capture defaults to regular files and deletions. Reject affected symlinks/reparse points, alternate-stream/path aliases, absolute/parent traversal paths, case-colliding names, special files, nested repositories, gitlinks/submodule changes and unsupported sparse-checkout/index states. Never traverse a directory reparse point to acquire bytes. Protected .git/.agents/.codex/.aws changes are not candidate work; locked tests/contracts require a separately approved revision. Untracked files must be individually enumerated and approved; ignored build outputs are inventoried, excluded and never force-added. Unsupported domains pause; they are not silently dropped from the diff. Submodule or symlink support would need its own exact capture/reconstruction contract.

Proposed conservative capture bounds are1024 changed paths and16MiB aggregate captured new bytes, with an explicit manifest/diff cap and existing bridge1MiB/event64KiB caps retained by using content references. These are reviewable initial product limits, not measured capacity claims or approved defaults. The formal revision must settle exact manifest/diff/per-file limits and overflow errors before tests/lock. Large patches fail before host commit and preserve evidence.

Text conversion must be explicit. Prefer byte-preserving object construction from captured content, never an unbounded git add -A over the current checkout. A base/current working-byte inventory distinguishes ordinary checkout line endings from edits. The approved diff must expose the exact proposed Git blob bytes/modes; no silent CRLF normalization, clean/smudge filter, working-tree-encoding or hook execution may substitute different bytes. Repositories requiring conversions/filters or mandatory signing/hooks need a reviewed trusted policy and a resulting-tree equality check, otherwise fail closed. No disable-hook/config trick is authorized by this proposal.

## Commit authority, concurrency and recovery

The trusted adapter acquires the SAME canonical checkout OS lock used for dispatch and presents the persisted intent/owner/generation before committing. Awaiting_commit retains a durable checkout fence even after the worker's process handles are clean. Scheduler/CLI claim, restart, repair and a second state root must all respect this fence. Releasing an OS handle during host handoff is permitted only after durable pending ownership is established; the next lock holder may be the matching trusted commit adapter, not a new inference writer. A malicious OS owner is outside this cooperative fence, but unexpected external mutation is detected and pauses.

Before effect, verify base HEAD/ref/index and current candidate inventory still match the captured approval. If a human/other process changed files, preserve both snapshots and stop; do not overwrite, resnapshot under old approval, reset or commit a mixture. In the separate-staging option, commit captured bytes without touching the dirty source; still retain its fence until the source disposition is explicit. Promotion back into a writable source must not discard its preserved edits.

Use a private host journal with states prepared, object_written, ref_applied, acknowledged. Persist the exact approved tree, parent, stable intent ID, immutable commit message/author/committer fields and expected new OID before mutating the publication ref. The adapter may use safe Git plumbing and a private index to construct objects from captured bytes, then compare-and-swap a dedicated task ref against the known prior OID. Local help confirms hash-object --no-filters, commit-tree with explicit parent and update-ref new/old OID interfaces; only their HELP was run here (each help exit129 is usage, not an executed commit). The formal design must prove durable object/journal ordering and required Git durability settings on Windows. Object creation does not itself publish a branch or constitute an ACK.

Commit ACK needs a new typed local-evidence shape: stable intent ID, task/issue/scope, generation, base parent, manifest/tree digest, new commit OID, exact task ref and host approval reference. It is not the current PR ACK with an invented GitHub URL. The host journal records the computed OID before ref mutation, making an interrupted response reconcilable without choosing new timestamps/creating duplicate commits. Independently inspect parent/tree/ref and bound approval on import. Duplicate identical ACK is idempotent; conflicting/unknown/stale/forged evidence rejects atomically.

If response or ACK is lost, first read the host journal and actual object/ref. Exact intended ref/head/tree/parent means applied; unchanged old ref with a durable unambiguous preparation means not applied and the SAME prepared effect may be resumed. Any different head, missing/corrupt journal, competing branch movement or uncertain disk outcome stays CommitUncertain/AwaitingHost and cannot rerun a worker or repeat a write on speculation. Reconcile object-written/ref-not-updated separately; unreachable objects are not publication. No automatic history search based only on message or a worker-supplied SHA. Host process descendants and lease follow the same bounded cleanup/ambiguity rules as workers.

Cancellation before preparation prevents commit; after object/ref uncertainty it records cancellation intent but reconciliation still determines whether the effect occurred. Never erase an already-created commit or rewind a ref automatically. A failed disk/rename/fsync/hook/signing check, snapshot overflow, dirty-input rejection, conflicting ACK or crash preserves audit/fence and no PR. Required journal/database/filesystem crash cuts belong in the formal acceptance plan, not just caller-supplied success booleans.

## Ordering after the commit ACK

Commit evidence proves only exact captured content was committed. Persist the new head, clear earlier verification/check/review evidence, and create the stable CreatePr intent for that head. The host publishes the exact dedicated ref (separate uncertain remote effect), fetches current remote head, creates/reconciles the PR, then runs required checks and obtains independent review of the committed diff. A draft PR may precede completed checks; applied RequestReview and Merge still require actual passing checks and approved independent review for that SAME new head. Any repair commit invalidates prior checks/review and requires fresh evidence. Merge ACK records real merge evidence; only then Done and independently reconciled issue completion. No old-base checks, precommit diff approval or worker statement can substitute final review/check evidence.

Historical revision2 pending CreatePr records require explicit migration quarantine: do not automatically ACK/publish existing unchanged-head dirty-checkout intents. Inspect and preserve their task/head/files, cancel or migrate through an approved disposition and fresh capture. Scope approvals remain exact-byte bound; changed workflow instructions require newly materialized approval where necessary. Never reserialize an old scope under its old hash.
